# Administration Type Check

Date: 2026-09-16

Issue: [#39](https://github.com/agentic-commerce-lab/merchant-quote-agent-plugin/issues/39)

## Status

Approved. No user was reachable during this work; every question that would
have gone to a human is recorded under [Questions not asked](#questions-not-asked)
with the assumption taken in its place.

## Context

The plugin's administration TypeScript — nine `.ts` files and six `.html.twig`
templates under `src/Resources/app/administration/` — has no type check and no
lint. `composer run quality:admin` covers only the three extracted pure modules
(`decision.ts`, `measures.ts`, `strategy.ts`) with assert-based self-checks,
because those are the only files testable without a toolchain. The components
were left out for the same reason. That asymmetry is the gap.

Two defects have already shipped through it, both while building #7:

1. `repository.aggregate(...)` — the admin JS `Repository` has no `aggregate`
   method. Every figure query threw `TypeError`, `loadFigures()` rejected, and
   the card stayed hidden behind its `v-if`. The feature did nothing at all.
2. A module navigation entry missing the required `id`, which Shopware's
   `Navigation` interface marks mandatory.

Both passed a clean admin build and a compiled-bundle grep, because neither
executes or type-checks the code.

A previous attempt (`scripts/lint-administration.sh`) tried to borrow the
shop's ESLint the way `scripts/test-integration.sh` borrows its PHPUnit. It
was removed because it could not run: no `npx` on the container's `PATH`, and
`./node_modules/.bin/eslint` failed with `Cannot find module 'typescript-eslint'`.

**That second failure is now diagnosed.** The shop's administration
`node_modules` holds 539 packages — a production-only install. `vue-tsc`,
`typescript-eslint` and `globals` are simply absent. Nothing about the shop's
`eslint.config.ts` is wrong; the dev dependencies were never installed. One
`npm install` in that directory fixes it, and 1083 packages arrive in about
nine seconds because the npm cache is warm.

## The decisive discovery

Shopware's administration package ships an official extension toolchain that
did not exist when #39 was filed:

```
vendor/shopware/administration/Resources/app/administration/extension-tooling/
    tsconfig.base.json    strict preset, resolves vue / @vue/* / src/* into the installed admin
    admin-types.d.ts      the live global.types.ts + entity schema + html shim
    eslint.mjs            parameterized flat-config factory
```

driven by three console commands:

```
bin/console administration:setup-extension-tooling      # generate configs + bridges
bin/console administration:generate-entity-schema-types # regenerate the entity schema
bin/console administration:check-extensions -- --only=X # vue-tsc + ESLint
```

This is the live installed type surface, not a curated or hand-written one. It
carries the real `Repository` class, the real `Navigation` interface, and the
shop's own generated entity schema — including this plugin's entities once the
schema is regenerated after install.

It is marked **EXPERIMENTAL**: the command names, flags and generated-file
layout can change in any release. That is an accepted risk, recorded in
[Risks](#risks).

## Decisions

### 1. Use Shopware's own toolchain, not a plugin-local one

The check is `bin/console administration:check-extensions --only=MerchantQuoteAgentPlugin`,
run in the test shop after `scripts/sync-to-shop.sh` — exactly the shape
`scripts/test-integration.sh` already uses for PHPUnit, and exactly the shape
issue #39's closing note asks for.

Two committed config files, both generated by `administration:setup-extension-tooling`
and both labelled `[commit this]` by it:

- `src/Resources/app/administration/tsconfig.json` — `extends` the generated bridge
- `src/Resources/app/administration/eslint.config.mjs` — composes the generated bridge

The bridge itself (`src/Resources/app/administration/.shopware/`) holds
machine-specific absolute paths into the installed administration. It is
git-ignored and regenerated on every run.

### 2. Adopt with a committed baseline

A first clean run reports **107 TypeScript findings and 570 ESLint findings**.
Fixing 677 findings is a different change from adding a check, and it would
mean ~107 type annotations and data-shape edits across five live component
files that no automated test renders.

The toolchain's own documented adoption path is a baseline, PHPStan-style:

```
bin/console administration:check-extensions -- --only=MerchantQuoteAgentPlugin --update-baseline
```

writes `.shopware-admin-baseline.json` at the plugin root, stored with paths
relative to that root so it travels with the plugin. Later runs report
`N new · M baselined` and fail only on **new** findings.

Matching is on file + code + message, ignoring line and column, so a finding
survives unrelated line drift and a genuinely new defect in an
already-baselined file is still new. This was verified, not assumed — see
[Acceptance evidence](#acceptance-evidence).

### 3. Regenerate the entity schema on every run

Before the schema is regenerated after a plugin sync, the plugin's own
entities are absent from `EntitySchema.Entities`, and every read through them
degrades to `never`. That alone accounted for 21 of the original 128 findings
and would make the baseline depend on when the schema was last generated.
`scripts/check-administration.sh` therefore runs
`administration:generate-entity-schema-types` on every invocation.

### 4. Install the administration's dev dependencies on demand

The script checks for `node_modules/vue-tsc` and runs `npm install` in the
administration directory only when it is missing. `npm install` rather than
the README's `npm ci`: `ci` deletes `node_modules` wholesale, and the shop is
shared with other agents who may be building admin assets at that moment.
`install` is additive against the same committed `package-lock.json`.

This keeps the constraint that the check is one command and not a
local-environment prerequisite.

### 5. Not wired into `composer run quality`, and not into CI

`composer run quality` is what `.github/workflows/quality-gate.yml` runs on a
GitHub runner with no database, no Shopware install and a 15-minute budget.
This check needs a booted Shopware with a database (for the entity schema) and
the administration's full `node_modules`. It cannot run there.

Wiring it into `quality` would therefore either break CI or force a silent
skip, and a gate that silently skips teaches exactly as little as a gate that
always fails. It lands as its own script, `composer run quality:admin:shop`,
alongside `composer run test:integration`, which has the same shop dependency
for the same reason.

The existing `composer run quality:admin` self-checks are untouched and stay
in `quality` and in CI.

### 6. No `package.json` and no lockfile in this repository

The toolchain and every version it pins are the shop's, governed by Shopware's
own committed `package-lock.json`. This change adds **zero** npm supply-chain
surface to this repository, which is why issue #63 (unpinned `jscpd`) needs no
companion decision here.

## Rejected alternatives

**A plugin-local `package.json` + `tsconfig.json` + hand-written
`shopware.d.ts`.** Self-contained and CI-capable, and it was the leading
candidate until the extension tooling turned up. Rejected on three counts:

- The declarations would be fiction maintained by hand against a moving
  vendor. `Repository` alone has 25 methods; the real one is already installed.
- Catching `aggregate()` needs Vue's `this` inference inside
  `Shopware.Component.register(name, {...})`. Without it `this.repository` is
  `any` and the call type-checks fine — the check would pass on the very bug
  it exists to catch. Getting that inference means a pinned `vue` dependency
  and reimplementing `ComponentOptions`' generic machinery.
- It adds the exact npm supply-chain surface decision 6 avoids.

**Adding `shopware/administration` to `require-dev` so CI can run vue-tsc
without a shop.** This does put `extension-tooling/` and the admin sources on
a GitHub runner. Rejected: the entity schema is generated from a live
database, so CI would run against the empty-schema stub and produce a
different finding set from a developer's shop. Two baselines for one check,
diverging, plus an `npm ci` of the full administration on every CI run.

**Borrowing the shop's ESLint directly, the original
`scripts/lint-administration.sh` approach.** Now known to fail only because of
the missing dev dependencies, so it could be revived — but it would hand-roll
config resolution that `administration:setup-extension-tooling` already does
correctly, and it would cover lint without type-checking, which is the lower
half of issue #39's own priority order.

**Running ESLint `--fix` first to shrink the baseline.** 8 errors and 112
warnings are auto-fixable, almost all `vue/max-attributes-per-line` in
templates. Rejected for this change: it reformats six `.html.twig` files and
buries the toolchain diff.

**Fixing all 677 findings instead of baselining.** See decision 2. It is a
worthwhile follow-up, not this change.

## Acceptance evidence

The deliverable is not the config file; it is proof the check catches the
class of defect that motivated the issue. With the full 677-finding baseline
in place and the check reading green, each defect was reintroduced into the
shop's copy of the plugin and the check re-run.

**Defect 1 — `repository.aggregate(...)`.** `search` changed to `aggregate` at
`page/merchant-quote-agent-list/index.ts:307`:

```
TypeScript ✖ 1 new · 106 baselined
  page/merchant-quote-agent-list/index.ts(307,62): error TS2339:
    Property 'aggregate' does not exist on type 'Repository<"merchant_quote_agent_decision">'.
✖ 1 checked · 1 with findings · 676 baselined · exit 1
```

**Defect 2 — navigation entry missing `id`.** `id: 'merchant-quote-agent'`
removed from the module's `navigation` array:

```
TypeScript ✖ 1 new · 107 baselined
  module/merchant-quote-agent/index.ts(136,9): error TS2741:
    Property 'id' is missing in type '{ label: string; color: string; ... }'
    but required in type 'Navigation'.
✖ 1 checked · 1 with findings · 677 baselined · exit 1
```

Both were reverted by re-running `scripts/sync-to-shop.sh`.

## What this does not cover

Stated plainly, because a gate whose reach is overstated is worse than none:

- **Icon names.** `icon: 'regular-robot'` — a name absent from Shopware's icon
  kit — was reintroduced and the check stayed **green**. `icon` is typed
  `string`, not a union of kit names. This was one of the two defects named in
  issue #39's body and the check does not catch it. Nothing short of a
  rendering smoke test or an icon-name union will.
- **Runtime behaviour.** Nothing renders a component. A method that type-checks
  and throws at runtime still ships. Issue #39's third option, the rendering
  smoke test, remains open and is still the only thing that closes this.
- **The 677 baselined findings.** Entries are keyed on file + code + message,
  each carrying a count. An added occurrence of an already-baselined message
  IS reported as new — verified by injecting one, which produced
  `TypeScript ✖ 1 new · 107 baselined` and exit 1. The residual hole is
  narrower: a change that both fixes one occurrence of a message and
  introduces a new, unrelated occurrence of the identical message in the same
  file leaves the count unchanged and is indistinguishable from the baselined
  original.
- **CI.** No GitHub runner runs this. Only a developer with the test shop does.
- **Shopware versions other than the test shop's.** The baseline was recorded
  against trunk (`6.7.9999999-dev`). A different version yields a different
  finding set.
- **`.js` sources.** `checkJs` is off in the preset. The three `.check.mjs`
  self-check files are not type-checked; `composer run quality:admin` executes
  them instead, which is stronger.

## Questions not asked

No user was reachable. Each assumption below is the one the implementation
takes.

1. **Baseline the 677 findings, or fix them in this change?**
   *Assumed:* baseline. Fixing them is a large diff across live component code
   with no rendering test behind it, and the vendor documents the baseline as
   the adoption path. A follow-up issue should shrink it.
2. **Composer script name.** *Assumed:* `quality:admin:shop`, which sorts next
   to the existing `quality:admin` and names its prerequisite.
3. **May the script run `npm install` inside the shared shop?**
   *Assumed:* yes, guarded on `vue-tsc` being absent, so it happens once.
   `install` not `ci`, to avoid emptying `node_modules` under another agent.
4. **Wire it into `composer run quality`?** *Assumed:* no. See decision 5.
5. **Run ESLint `--fix` on the 120 auto-fixable template findings now?**
   *Assumed:* no. Separate, noisy, unrelated to landing the gate.
6. **Retitle issue #39?** The issue comment suggests *"No type check or lint
   over the administration components"*. *Assumed:* the coordinator decides;
   this work neither retitles nor closes the issue.

## Risks

- **The toolchain is EXPERIMENTAL.** Command names, flags and generated-file
  layout can change in any Shopware release. Mitigation: the check lives in
  one script, the two committed configs are small, and a breakage surfaces as
  a tooling error rather than a false green — `administration:check-extensions`
  reports `TOOLING ERROR` and exits 1 when `vue-tsc` is missing, which is how
  the missing dev dependencies were found.
- **Shopware 6.7.1, the plugin's floor, may not ship this tooling.** The check
  is a development gate run against the trunk test shop, not a supported-version
  claim. It does not affect what the plugin requires at runtime.
- **Baseline drift across shops.** A shop on a different Shopware version
  produces different findings, which read as new and fail the check. This is
  the main reason it is not in `composer run quality`.

## Testing

The check is itself a test, so its verification is behavioural:

1. `composer run quality:admin:shop` exits 0 against unmodified `main`.
2. Reintroducing `aggregate()` makes it exit 1 with the finding reported as
   new. Reverting returns it to 0.
3. `composer run test` and `composer run quality` stay green — the change adds
   files and one composer script, and touches no PHP.
4. `scripts/check-administration.sh` is idempotent: a second consecutive run
   reports the same result and rewrites no committed file.
