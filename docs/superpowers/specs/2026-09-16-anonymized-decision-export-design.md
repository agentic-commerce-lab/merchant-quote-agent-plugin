# The anonymized decision export

Date: 2026-09-16

## Status

Approved. Written for issue [#34](https://github.com/agentic-commerce-lab/merchant-quote-agent-plugin/issues/34)
(2.4b), which carries the third and last Done-when of
[#19](https://github.com/agentic-commerce-lab/merchant-quote-agent-plugin/issues/19):

> The export contains no raw identifier; a test greps for the fixture's email
> and customer number and finds neither.

Builds on
[`2026-08-29-quote-decision-audit-design.md`](2026-08-29-quote-decision-audit-design.md),
which owns the table this reads, and on
[`2026-09-16-preflight-escalation-record-design.md`](2026-09-16-preflight-escalation-record-design.md),
which added a row shape the export has to handle.

## Context

`merchant_quote_agent_decision` is the plugin's observability record: one row
per servicing pass, written by `DecisionRecorder` through
`DecisionRecordWriter`. #7 renders it, #21 aggregates it. This issue adds the
third reader — a console command that writes the table out as JSONL for a
merchant to send to Shopware, so that strategies can be improved from more than
one shop's negotiations.

The purpose is what fixes the design. This is not "a data dump with the obvious
fields removed". It is a merchant handing business records to a third party on
the strength of a promise about what is in them. The promise has to be one the
merchant can check by reading a page, and the code has to be built so that the
promise cannot quietly stop being true.

### What is actually in the table

Read off `QuoteDecisionRecord` today, not off #34's body, which predates four
changes to the entity. Grouped by what the field can carry:

**Machine values, no free text, no identifier.** `currencyIso`,
`triggerReason`, `attempt`, `band`, `outcome`, `escalationReason`,
`discountPercentGranted`, `maxDiscountPercent`, `totalNetBefore`,
`totalNetAfter`, `model`, `modelHost`, `extractPromptHash`,
`negotiatePromptHash`, `replyPromptHash`, `promptTokens`,
`completionTokens`, `modelLatencyMs`, `durationMs`, `authorized`, `verified`,
`errorClass`, `terminalState`, `terminalAt`, `resolvedState`, `resolvedAt`,
`revisionUpdatedAt`, `createdAt`. `writes` belongs here too: `OfferApplier`
builds it from a closed set of method names (`claim`, `updateLineItems`,
`updateQuote`, `recalculate`), never from data.

**Shop-local identifiers.** `id`, `quoteId`, `customerId`, `salesChannelId`,
`revisionVersionId`, `strategyVersionId` — UUIDs. `quoteNumber` — a
merchant-readable document number.

**Free text, model-authored or buyer-derived.** `rawProposal`, `replyToBuyer`,
`violations`, and two leaves inside `interpretedAsks`
(`clarificationQuestions`, `humanReviewRequests`).

**Business data inside a JSON column.** `historyReads.rounds[].result` is the
string `HistoryRequestResolver` renders into the prompt. It contains past quote
numbers, order numbers, product labels and money. `errorChain[].message` is a
throwable's message, which can carry anything the throwing code chose to put
in it.

### What changed since #34 was written

Four things, checked against the entity rather than assumed:

1. **`buyerComment` is now `replyToBuyer`** (renamed 2026-09-04,
   `Migration1788525369RenameBuyerCommentToReplyToBuyer`). #34's body says the
   field "holds the verbatim text sent to the buyer" and then calls it a
   "buyer comment". The entity docblock settles it: it is *the agent's message
   to the buyer*, written only by `DecisionRecorder::recordReply()`, and **the
   buyer's own words are never stored in this table at all** — only their
   interpreted ask. This matters in both directions. Under-redacting: the field
   is not the buyer talking, so it is not automatically personal data, and
   treating it as untouchable would be wrong. Over-redacting: the agent's reply
   is still free text generated by a model that was shown the buyer's message,
   so it can echo anything the buyer typed. It stays behind the flag — for the
   second reason, not the first.

2. **`strategyVersionId`** (#99) — which prompt version this pass actually
   sent.

3. **`terminalState` / `terminalAt`** (#33) and **`resolvedState` /
   `resolvedAt`** — stamped later by subscribers, not by the pass. Both are
   enums plus timestamps; both are exactly the outcome signal that makes the
   export worth sending, since without it nobody can tell a good offer from a
   bad one.

4. **Refusal rows** (#35, `DecisionRecorder::recordRefusal()`). A refusal row
   has no model call, no reply, no band, no duration: `outcome = escalated`,
   `escalationReason = not_configured`, and `violations` holding the
   configuration's own complaints. Nothing special is needed for it — every
   affected field is already nullable and the exporter emits nulls — but it is
   the reason the export must not filter on "had a model call", and it is the
   reason `violations` is not always model text (see Decision 2).

## Questions I would have asked

The house workflow is a dialogue; this ran without one. Each question below is
recorded with the assumption taken in its place, so a reviewer can overturn the
assumption rather than reverse-engineer it.

1. **Should `--from` / `--to` be required, or should omitting them export
   everything?** *Assumption: required.* #34 and #19 both write them without
   brackets while bracketing `[--include-comments]`, and an export with no
   range is the one command invocation a merchant can run by accident and
   regret. A merchant who wants everything can pass a wide range and will have
   meant it.

2. **Should the salt be regeneratable from the console (`--rotate-salt`)?**
   *Assumption: no.* Nobody has asked, rotation breaks comparability with every
   export already sent, and a merchant who genuinely needs a clean break can
   delete the `system_config` row. Adding a flag for it is speculative.

3. **Should the export be filterable by sales channel?** *Assumption: no.* Not
   asked for, and `salesChannel` is in the output for grouping after the fact.

4. **Is `modelHost` acceptable to send at all?** It is a hostname the merchant
   chose, which can identify a private gateway. *Assumption: yes, keep it.* #34
   explicitly asks for it to be documented rather than removed, and the
   provider a shop negotiates against is a first-order variable for the
   strategy work this export exists to feed.

5. **Should the output be a file argument instead of stdout?** *Assumption:
   stdout.* `> quotes.jsonl` is the Unix answer and needs no code; the notices
   go to stderr so the redirect stays clean.

## Decisions

### 1. An allowlist mapper, not a redactor

The export is built field by field from a named list. It never takes the row
and removes things from it.

This is the decision everything else rests on. A denylist is only correct until
the next column lands: #19's table has gained six columns in three weeks, from
four different issues, none of which had this export in view. Under a denylist
each of those would have shipped straight into the export, and the failure mode
is silent — an exported file that is one field wider than the promise made to
the merchant, discovered by whoever reads it at Shopware.

Under an allowlist the failure mode is the opposite and harmless: a new column
simply does not appear until someone adds it. To make even that visible,
`ExportFieldCoverageTest` reflects over `QuoteDecisionRecord`'s public
properties and fails if any of them is absent from the exporter's own
classification table. Adding a column then forces one line saying what the
column is — exported, pseudonymized, free text, or dropped — which is exactly
the decision that should not be made by omission.

### 2. `--include-comments` gates `rawProposal`, and everything else that is free text

**Yes, it gates `rawProposal`.** The argument is not a judgement call about how
likely the model is to quote someone; it is what the field provably contains.
`OfferProposer` sets it to `json_encode($response)` of a `NegotiateResponse`,
whose `message` is the sentence the buyer is about to be shown, composed by a
model whose user prompt carried the buyer's comment verbatim.
`docs/for-merchants.md` already states the consequence for the outbound side:

> The one thing outside your control is the message itself — whatever the
> customer typed is sent as they wrote it, so if they sign it or include a
> phone number, that text goes with it.

A buyer who signs a message with their name and direct line has put that in the
model's context, and the model's answer is free to repeat it. Pseudonymizing
`customerId` to a HMAC while shipping a `rawProposal` that opens "Dear Ms
Müller, regarding your account 10042" would not be a partial protection; it
would be a protection that is void for exactly the records that matter, and
worse than none because the merchant was told the file was anonymized.

The same argument, made once, decides three more fields rather than leaving
them to be noticed separately:

- **`violations`** is model text on at least one path.
  `OfferProposer::propose()` passes `$response->escalationReason` — a free-text
  string the model wrote — into `ProposedAnswer::escalate()`, and
  `DecisionRecorder::recordProposal()` stores it as the sole element of
  `violations`. On other paths the same column holds policy strings from
  `OfferAuthorizer` or `InvalidQuoteAgentConfiguration`, which are safe. Export
  time cannot tell the two apart, so the column follows its worst path. The
  analytic signal is not lost: `escalationReason` is an enum
  (`QuoteEscalationReason`), always exported, and it is what counts and groups.
  `violations` is the prose underneath it.

- **`interpretedAsks.clarificationQuestions` and `.humanReviewRequests`** are
  lists of strings the extraction model wrote while reading the buyer's
  message. Everything else under `interpretedAsks` is a typed ask —
  `PriceAsk` is two scalars, `StructuralAsks` is quantities and product refs,
  `NegotiationAsks` is delivery/payment/bundle terms — and that structured part
  is precisely what the strategy work wants. The two string lists are the only
  leaves that are prose, and they go behind the flag.

- **`errorChain[].message`.** `class` and `at` stay, because an exception class
  and a file:line are ours, not the buyer's. The message is whatever the
  throwing code chose, including a provider response body that can quote the
  prompt.

The flag keeps #34's name — it is written into two issues and is about to be
written into the merchant documentation — but it means "include free text",
and the help text, the exclusion notice and the docs all say so in those words.
Renaming it to `--include-free-text` was considered and rejected as churn
against a name the PM has already seen; the wider meaning is stated everywhere
the flag is.

### 3. `historyReads.rounds` keeps the question and drops the answer

`rounds[].result` is `HistoryRequestResolver`'s rendered block. Sampled from
its own `sprintf`s, it reads:

```
- quote QU10042, 2026-08-14, 4,250.00 EUR net, state accepted, converted yes, ...
- order 10009, 2026-07-02, 1,180.00 EUR net, state open
  - Aluminium bracket 40x40: quantity 120, unit net 3.75 EUR
```

Past quote numbers, past order numbers, product labels and figures for one
named account. That is not a candidate for the free-text flag; it is the
merchant's and their customer's commercial history, and there is no reading of
"anonymized export" under which it leaves. It is dropped unconditionally.

What survives is `kind` — `quote_history`, `orders`, `product_purchases` —
which answers the question the export is for: does letting the agent read
history change what it decides? `productId` goes with the result: a shop-local
product UUID means nothing to a second shop, so it is cost without benefit.

The summary half of `historyReads` is kept whole. Every field on it is a count,
a total, a percentage or an availability reason — `quotesSeen`,
`offersAccepted`, `lastGrantedDiscountPercent`, `orderCount`, `lifetimeNet`,
`lastOrderAt`. These are the account's shape, not its identity, and #34 keeps
amounts.

### 4. `quoteNumber` is dropped, every UUID is pseudonymized

`quoteNumber` is a document number a human reads, printed on the quote the
buyer received. It is the merchant's own primary handle on a specific deal with
a specific company, and — unlike a UUID — it is short enough to recognise and
often sequential enough to leak volume. Nothing in cross-shop strategy work
needs it. Dropped.

The UUIDs are pseudonymized rather than dropped, because their *grouping* is
the analytic value and their *identity* is the risk:

| Field | Exported as | Why not dropped |
| --- | --- | --- |
| `id` | `id` | Lets a second export of an overlapping range be deduplicated. |
| `quoteId` | `quote` | Several passes negotiate one quote; a negotiation is the unit of study. |
| `customerId` | `customer` | Repeat-buyer effects are unreadable without a stable account key. |
| `salesChannelId` | `salesChannel` | Separates channels with different policies. |
| `revisionVersionId` | `revision` | Shows two passes acting on the same revision. |
| `strategyVersionId` | `strategyVersion` | Groups passes by prompt version. |

`strategyVersionId` is pseudonymized even though built-in strategies are seeded
by migration with ids that could be identical across shops. Cross-shop prompt
grouping is already available and better served by `extractPromptHash`,
`negotiatePromptHash` and `replyPromptHash`, which are content hashes and are
exported raw. That makes the shop-local id pure risk, so it is salted like the
rest.

**Pseudonym construction.** `hash_hmac('sha256', $value, $salt)` truncated to
32 hex characters. Truncation is cosmetic — it keeps a JSONL line readable —
and 128 bits is not a collision concern at these volumes. The input is the
value as the DAL hands it over (lowercase hex for a UUID), so the same id
pseudonymizes identically everywhere it appears.

### 5. The salt lives in `system_config` and is created on first export

Key: `MerchantQuoteAgentPlugin.export.pseudonymSalt`, deliberately outside the
`MerchantQuoteAgentPlugin.config.*` prefix the admin settings form renders —
the same reasoning `A2cnKeyStore` documents for the signing key. A salt shown
in a config form is a salt that gets copied into a support ticket.

`AGENTS.md` says merchant configuration is never read from `system_config`
directly — it goes through `Config\QuoteAgentSettingsReader`. The salt is not
merchant configuration: it is plugin-owned material the merchant never sets,
like the A2CN signing key, which reads `SystemConfigService` directly for the
same reason. `ExportSalt` follows `A2cnKeyStore`, not the settings reader.

`ExportSalt::current()` reads it and generates one from
`random_bytes(32)` if it is absent, then persists it. This is the point where
it deliberately differs from `A2cnKeyStore`, which throws instead:

- A signing key generated lazily can be generated *twice* by two concurrent
  requests, and every act signed with the loser stops verifying. The damage is
  silent and permanent, so a loud refusal is better.
- A salt has no such failure. Two concurrent generations are not possible in
  practice — this runs from one console process, at a merchant's hand, never
  from a request — and if one somehow occurred, the cost is that two exports
  are not linkable to each other. That is a degraded correlation, not corrupted
  evidence.
- Refusing instead would mean a merchant who installed the plugin before this
  version cannot export at all until they reinstall it. Generating covers every
  existing install with no migration and no install-hook change.

This is also the answer to "what happens if it is missing": the first export
creates it, silently and once. `ExportSalt` is the only writer. The docs state
the consequence plainly — deleting that row makes future exports incomparable
with past ones, which is a valid way to break the link on purpose and a bad
accident otherwise.

### 6. `unparsable-host`

`modelHost` is `ModelPlatform::hostOnly($access->baseUrl)`, which tries
`parse_url()`, retries with an assumed scheme for a merchant who typed a
base URL without one, and falls back to the literal string `unparsable-host`.
The fallback exists because the raw base URL can carry an API key in its query
string, and this value lands in a merchant-readable audit column, so the one
thing it must never be is the input.

It is not a bug and it is not a redaction the export performs; it was already
in the row. The export format documentation says so, in one line, wherever
`modelHost` is described — otherwise the first person to read an exported file
files it as one.

### 7. Shape, and who does what

Four classes, none of which is an abstraction over one implementation:

- **`DecisionExportCommand`** (`src/Command/`) — options, date parsing, the
  exclusion notice, iteration. Follows the two existing commands: `#[AsCommand]`,
  `final`, `SymfonyStyle`, `->tag('console.command')` in `services.php`.
- **`ExportSalt`** — the `system_config` read/generate above.
- **`DecisionPseudonym`** — the HMAC, constructed once per run with the salt.
- **`AnonymizedDecision`** — the allowlist mapper: record in, ordered
  `array<string, mixed>` out, plus the `FIELDS` classification table
  `ExportFieldCoverageTest` reflects against.

**Reading.** `RepositoryIterator` over `merchant_quote_agent_decision.repository`
with a `RangeFilter` on `createdAt` and a `FieldSorting` on it, which is the
index `Migration1787998662CreateQuoteAgentDecision` already declares
(`idx.mqad.created_at`). Paging through the DAL rather than issuing DBAL keeps
the JSON columns decoded and the entity the single source of the shape.

**Writing.** One `json_encode` per row to `$output`, newline-terminated.
Notices — how many rows, and whether free text was excluded — go to the error
output via `$io->getErrorStyle()`, so `merchant-quote-agent:export … > out.jsonl`
produces a file containing only JSONL. The exclusion notice is not optional
and not silent: #34 asks for the command to say when it excludes comments, and
it says it on every run that excludes them, naming the flag.

## The no-raw-identifier test, and why it is not vacuous

#19's Done-when is a grep. A grep passes trivially against a fixture that never
contained the string, which is the specific way this test fails to mean
anything. Four things stop that.

**1. The fixture plants the identifiers where they can really occur.** Not in
one field, in every field that can carry them, chosen from the analysis above
rather than from convenience. A record is written with a real `customerId`, a
`quoteNumber` of `QU10042`, and the strings `anna.mueller@acme.example` and
`10042` appearing in `replyToBuyer`, `rawProposal`, `violations`,
`interpretedAsks.humanReviewRequests`, `historyReads.rounds[].result` and
`errorChain[].message`.

**2. A positive control proves the grep can find them.** The same record is
exported a second time with `--include-comments`, and the test asserts the
email **is** present in that output. If the fixture had failed to carry the
email, or the exporter had silently emitted nothing, or the grep were looking
at the wrong bytes, this assertion fails. It is the assertion that converts
"finds neither" from an absence into evidence.

**3. A completeness control proves the default export is not empty.** The
default run asserts the analytic fields are there — `outcome`, `band`,
`discountPercentGranted`, `terminalState` — so the test cannot pass by
exporting a blank line.

**4. `--include-comments` is asserted not to widen anything else.** Even with
the flag, the raw `customerId` hex, the `quoteNumber` and the history block
must be absent. The flag adds free text; it never turns anonymization off.

The unit level carries the field-by-field assertions on `AnonymizedDecision`,
plus `ExportFieldCoverageTest`. The integration level
(`tests/Integration/DecisionExportTest.php`) runs the real command against the
real DAL, because the grep is only worth anything over bytes that actually came
out of the shop.

## What leaves and what does not — the merchant-facing statement

Documented in `docs/for-merchants.md` under *Costs and data*, which is where
the plugin already tells merchants what is sent where, and referenced from
`README.md`'s documentation list. Stated as three lists, not as prose:

**Leaves, as a salted pseudonym** — the row, quote, customer, sales channel,
quote revision and strategy version. The same account is the same string in
every export from this shop and a different string in every other shop's.

**Leaves, as itself** — when it happened, what was asked and what the rules
allowed, the money and the percentages, the decision and why, the prompt
version hashes, the model name and host, tokens, timings, and how the quote
ended.

**Does not leave, ever** — names, e-mail addresses, postal addresses, phone
numbers, company names; the quote number; the account's past quote and order
history block; the buyer's own message (which is not in the record in the first
place).

**Does not leave unless `--include-comments`** — the agent's replies, the
model's raw answers, escalation prose, the model's clarification and
human-review questions, and error messages.

With the line about `unparsable-host` beside the `modelHost` entry.

## Not here

Retention or pruning (#19 left it to the merchant). Scheduling — #34 says a
merchant action, never automatic, and nothing here registers a task. Any
transport: the command writes to stdout and the merchant decides what to do
with the file. The admin page over the trail is #7; signatures are #20.
